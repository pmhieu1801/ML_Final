1. Official Final Project Handout
1.1. Project Overview
In the midterm project, students implemented a basic machine learning pipeline for predicting whether a student receives a scholarship. The project focused on the essential stages of a classical machine learning workflow, including exploratory data analysis, data preprocessing, model training, model evaluation, and error analysis.
In the final project, each team will extend that midterm system into a more rigorous and better-justified machine learning solution. The objective is not merely to train models and report metrics. Instead, the final project is intended to assess whether students can:
establish a clear baseline system,
compare multiple models systematically,
improve the original pipeline in a meaningful way,
evaluate model behavior using appropriate metrics,
analyze errors in a structured manner,
interpret the resulting model,
and present the complete work in a professional technical report.
This final project is designed to simulate a more complete applied machine learning workflow while remaining appropriate for an introductory course in machine learning.
1.2. Team Policy
Students must work in teams of two.
All team members are expected to contribute substantially to the project.
The final report must include a short statement describing the contribution of each team member.
1.3. Problem Statement
The dataset contains records of students in a hypothetical country. Each record describes a student using academic and socio-economic attributes. The task is to build a machine learning system that predicts whether a student receives a scholarship.

1.5.3. Task 3. Data Preprocessing
Teams must apply appropriate preprocessing steps and justify each decision. Possible preprocessing steps include:
handling missing values,
encoding categorical variables,
normalization or scaling,

one linear model, preferably Logistic Regression;
one tree-based model, such as Decision Tree or Random Forest;
one additional classical machine learning model, such as SVM, KNN, Gradient Boosting, XGBoost, or another approved method.
The goal is to compare models with different inductive biases and practical trade-offs.

2. Companion Guide for Students
This companion guide provides additional guidance for parts of the project that students often perform superficially or incorrectly. It is not a solution manual. Instead, it is intended to help teams meet the expected academic and technical standard of the final project.
2.1. How to Conduct Exploratory Data Analysis Properly
Exploratory Data Analysis (EDA) is not a collection of random charts. Its purpose is to help you understand the data and support later modeling decisions.
A good EDA section should help answer questions such as:
How many samples and features are there?
Which variables are numerical, and which are categorical?
Is the target variable balanced or imbalanced?
Are there suspicious values, missing values, or unusual distributions?
Which variables appear to be related to scholarship status?
Recommended analyses include:
summary statistics for numerical features,
frequency tables for categorical features,
target distribution,
histograms or boxplots for important numerical variables,
bar charts for important categorical variables,
and correlation analysis where appropriate.
Common mistakes include:
presenting many charts without explanation,
writing observations that are obvious but not useful,
discussing plots that do not influence later decisions,
and confusing correlation with causation.

2.2. Preprocessing Decision Guide
Preprocessing should be motivated by the properties of the data and the requirements of the model.
Typical preprocessing tasks include:
missing-value imputation,
categorical encoding,
scaling or normalization,
and proper splitting of train, validation, and test data.
Examples of good reasoning:
Logistic Regression and SVM often benefit from feature scaling.
Tree-based models usually do not require scaling.
One-hot encoding is often suitable for nominal categorical variables.
Missing values should be handled using a reproducible method rather than arbitrary manual edits.
Important Warning: Data Leakage
Teams must avoid leakage. For example:
do not fit a scaler on the full dataset before splitting;
do not tune hyperparameters directly on the test set;
do not construct features using label information in an improper way.
2.3. Model Comparison Guide
Training multiple models is meaningful only when the comparison is well reasoned.
At minimum, teams should discuss:
which model performs best overall,
whether some models achieve higher precision but lower recall,
whether a more complex model actually yields meaningful improvement,
and whether the best model is also the most practical one.

2.4. Hyperparameter Tuning Guide
Hyperparameter tuning is one common way to improve the system, although it should be performed in a controlled and meaningful way.
Recommended approach:
choose one or two promising models,
define a small and reasonable search space,
use cross-validation or a proper validation split,
and report both the selected parameters and the resulting performance changes.
Examples of parameters that may be tuned:
Logistic Regression: C, penalty type;
Decision Tree:max_depth, min_samples_split;
Random Forest:n_estimators, max_depth;
SVM: C, kernel, gamma.
Common mistakes include:
tuning too many parameters blindly,
tuning directly on the test set,
and reporting the best score without explaining why the change matters.

2.6. Interpretation Guide
Interpretability means explaining model behavior in a technically responsible way.
Possible methods include:
Logistic Regression coefficients,
feature importance from tree-based models,
permutation importance.
Teams should discuss:
which features seem most influential,
whether the model's behavior matches domain intuition,
and whether any apparently important feature raises practical or ethical concerns.
Important Caution
A feature being important does not prove causation. Students must avoid causal claims that are not supported by the project design.
